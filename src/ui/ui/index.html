STURM + Gateway UI integration board

This board turns the new STURM/Gateway design direction into a concrete integration plan. The goal is one shared shell, one shared component language, truthful live data surfaces, and a staged rollout across STURM, Gateway, and sister product surfaces.

integration principles

How to integrate this without design drift

Truth over mockups, shared assets over duplicated one-off CSS.
1. Canonical shared system

Keep /v6/sturm.css as the canonical shared design language first, then extract stable primitives into src/ui/design-system once STURM and Gateway both use them.

2. Shell before depth

Migrate navigation, layout, headers, panels, tables, status badges, and forms first. Deep workflow-specific screens come after the shell and information architecture stop moving.

3. Live runtime, not fantasy UI

Gateway and STURM surfaces must read from real APIs and expose truth states. If a panel is partial or seeded, mark it that way instead of polishing inaccurate states.

task list

Concrete integration tasks

Each task has a direct deliverable and a definition of done.
T-01

Freeze the shared UI contract

Audit the currently duplicated UI assets across src/ui/, src/ui/v6/, and src/ui/design-system/. Decide which tokens and primitives are canonical, then retire the duplicates instead of letting STURM and Gateway drift.

  • Pick the canonical token source for color, spacing, elevation, radius, badges, tables, and forms.
  • Normalize shared classes for truth-state badges, shell cards, split panes, nav groups, and monospace metadata chips.
  • Document which files are legacy, transitional, and canonical.
deliverable
Shared UI inventoryOne canonical CSS/component map for both STURM and Gateway.
done when
No duplicate primitivesBoth products consume the same badge, panel, nav, and table language.
T-02

Migrate the STURM top-level shell

Promote the new design from isolated v6 pages into the main STURM experience. The first wave should cover the entry shell and the most-used operator surfaces.

  • Map src/ui/v6/index.html onto the default STURM landing experience.
  • Bring designer, OCR studio, and workspace surfaces onto the shared navigation and panel primitives.
  • Keep existing APIs and flows stable while re-skinning the shell.
deliverable
Unified STURM shellLanding, designer, and OCR views all speak the same UI language.
done when
Operator surfaces feel consistentNo abrupt jumps between legacy and new shell components inside STURM.
T-03

Migrate the Gateway control plane

Use the new Gateway shell as the control-plane baseline, then wire every major view to the same shared truth-state vocabulary used by STURM.

  • Adopt the new sidebar/header/panel layout from src/ui/v6/gateway.html and the companion gateway-app.jsx flow.
  • Normalize cards for agents, containers, chain state, runtime registry, health, and model connectivity.
  • Expose partial/seeded/live markers consistently so operators see real runtime posture.
deliverable
Gateway UI parityControl-plane views match STURM design quality while staying operationally truthful.
done when
Operators can cross-read both productsSame mental model for status cards, tables, badges, and actions.
T-04

Create a subsidiary surface template

After STURM and Gateway converge, package the common shell into a reusable template for sister surfaces. The goal is shared UX grammar with product-specific content, not cloned one-off sites.

  • Define a standard shell for list/detail dashboards, task boards, registry pages, and cockpit views.
  • Keep product-specific accents optional while preserving shared layout, typography, and component rhythm.
  • Apply first to the highest-value sister surfaces next, not all at once.
deliverable
Surface starter kitRepeatable HTML/CSS/JS scaffold for related products.
done when
New surfaces stop reinventing shellsTeams can launch sibling views from one proven baseline.
T-05

Wire every visible state to real data

The new UX only holds if every headline KPI and health chip reflects runtime truth. This is where design and product integrity meet.

  • Back panels with real APIs, or explicitly mark them seeded/partial when not yet live.
  • Add freshness timestamps and provenance labels where operators need trust.
  • Remove any leftover fantasy counts, dead counters, or decorative status chips with no backing source.
deliverable
Truthful runtime surfacesStatus cards, registry tables, and live health views all explain their source.
done when
No ambiguous status UIUsers can tell live, partial, seeded, and unavailable states at a glance.
T-06

Run QA, route audit, and rollout cleanup

Close the integration with screenshot checks, responsive verification, route consolidation, and dead-asset cleanup before making the new shell the default everywhere.

  • Smoke critical routes on desktop and mobile widths.
  • Check all static asset paths, redirects, and browser console noise.
  • Delete or archive legacy duplicate files after the replacement surfaces are proven.
deliverable
Release-ready migration setVerified routes, responsive screens, and a smaller long-term UI surface area.
done when
Default route cutover is safeNo missing assets, dead links, or broken operator workflows.
