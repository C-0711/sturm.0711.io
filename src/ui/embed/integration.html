STURM × cb-chat — Integration Guide

Dieses Dokument beschreibt die zwei Integrationspfade zwischen cb-chat.0711.io und playground.0711.io:

  1. Server-zu-Server Import — cb-chat-Backend ruft STURM auf, lädt Dokumente eines Falls als Workspace ein.
  2. Embed im iframe mit Session-Exchange — cb-chat-Frontend bettet einen STURM-Workspace als iframe ein, ohne Tokens in URLs zu exponieren.

Beide Pfade erlauben zusätzlich Webhooks für Live-Notifications (siehe unten).

1. Token ausstellen (einmalig)

Vor allem anderen brauchst du ein WorkspaceToken mit embed-Scope. Das ist ein langlebiger Bearer-Token den cb-chat-Backend behält. Aussstellung via Admin-Bearer:

curl -X POST https://playground.0711.io/api/workspaces/<wsId>/tokens \
  -H "Authorization: Bearer <ADMIN_BEARER>" \
  -H "Content-Type: application/json" \
  -d '{"scopes":["embed","read"], "label":"cb-chat-prod", "expiresInDays":365}'

Antwort enthält den secret einmalig:

{
  "token": { "id": "wsk_…", "scopes":["embed","read"], "label":"cb-chat-prod", … },
  "secret": "<SECRET — speichern!>",
  "message": "Save this secret — it cannot be retrieved later."
}
Der Secret wird nie wieder ausgespielt. cb-chat-Backend muss ihn sicher speichern (env-var oder Secret-Manager). Bei Verlust: Token revoken (DELETE), neuen ausstellen.

2. Embed-iframe mit Session-Exchange (sicher)

Drei Schritte: cb-chat-Backend erstellt eine kurzlebige Session, cb-chat-Frontend embedded den iframe und liefert die Session via postMessage, der iframe tauscht die Session gegen ein HttpOnly-Cookie.

Schritt A — cb-chat-Backend: Session erzeugen

// Node-Beispiel
const resp = await fetch(`https://playground.0711.io/api/workspaces/${wsId}/sessions`, {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${WSK_SECRET}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ ttlMs: 3600000 }),  // 1h
});
const { sessionId, expiresAt } = await resp.json();
// → sessionId an Frontend weiterreichen (über deinen normalen Auth-Pfad)

Schritt B — cb-chat-Frontend: iframe + postMessage

<iframe id="sturm-frame"
  src="https://playground.0711.io/embed/workspace.html?ws=<wsId>"
  style="width:100%; height:100vh; border:0"
  allow="clipboard-write"></iframe>

<script>
const STURM_ORIGIN = 'https://playground.0711.io';
const frame = document.getElementById('sturm-frame');

// Wait for iframe to signal it's ready
window.addEventListener('message', (ev) => {
  if (ev.origin !== STURM_ORIGIN) return;
  if (ev.data?.type === 'sturm:ready') {
    // Send session — targetOrigin REQUIRED, never use '*'
    frame.contentWindow.postMessage(
      { type: 'sturm:auth', sessionId: '<sessionId from Schritt A>' },
      STURM_ORIGIN
    );
  }
});
</script>

Der iframe redirected dann automatisch in /workspace.html?ws=… mit gesetztem sturm-session Cookie.

Warum Session statt Token in der URL? Tokens in Query-Parametern landen in Server-Logs, Browser-History, Referrer-Headern. Eine kurzlebige Session-ID, die nur einmal benutzbar ist und sofort gegen ein HttpOnly-Cookie getauscht wird, ist isoliert vom URL-Bus.

3. Server-zu-Server Import (cb-chat → STURM)

Lädt alle Dokumente eines cb-chat Falls als Workspace ein. Im Hintergrund läuft ein Job (Phase C); fortschritt-trackbar.

curl -X POST https://playground.0711.io/api/integrations/cb-chat/import \
  -H "Authorization: Bearer <ADMIN_BEARER>" \
  -H "X-CBChat-Cookie: <USER_SESSION_COOKIE>" \
  -H "Content-Type: application/json" \
  -d '{"fallId":"886a96f8-…", "workspaceName":"Maerzhaeuser Madeleine"}'
{
  "jobId": "…",
  "workspaceId": "maerzhaeuser-madeleine",
  "workspaceUrl": "/workspace.html?ws=maerzhaeuser-madeleine",
  "jobEventsUrl": "/api/jobs/<jobId>/events?live=true",
  "status": "queued"
}

Subscribe to jobEventsUrl via SSE für Live-Progress, oder polle GET /api/jobs/<jobId>.

4. Webhooks (Live-Notifications)

STURM emittiert pro Workspace-Mutation ein signiertes Event an alle registrierten Subscriber:

Event-TypeWannPayload-Keys
document.classifiednach Mistral-Small-KlassifikationdocUuid, label, confidence, kpiCount, displayName
document.extractednach Mistral-OCR-ExtraktiondocUuid, templateId, pages, hallucinationCount
document.auditednach Audit-RundocUuid, auditKind, totals
document.approvednach approve via PATCHdocUuid, approvedAt, templateId
master.updatedwenn neuer master.json-Snapshot persistiert wirdverlaufHash, approvedCount, signature

Subscriber registrieren

curl -X POST https://playground.0711.io/api/workspaces/<wsId>/webhooks \
  -H "Authorization: Bearer <ADMIN_BEARER>" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://cb-chat.0711.io/api/sturm-webhook",
    "events": ["document.classified","master.updated"],
    "label": "cb-chat-fall-listener"
  }'

Antwort enthält den secret für Signatur-Verifikation:

{
  "id": "sub_…",
  "url": "https://cb-chat.0711.io/api/sturm-webhook",
  "secret": "<HMAC-SECRET>",
  …
}

Signatur verifizieren (Receiver-Seite)

Jede Webhook-Delivery hat den Header X-Sturm-Signature: t=<ms>,v1=<hex>. Verify so (Stripe-Style):

const crypto = require('node:crypto');

function verifyWebhook(body, signatureHeader, secret) {
  const [tPart, vPart] = signatureHeader.split(',');
  const t = tPart.split('=')[1];
  const v1 = vPart.split('=')[1];
  const expected = crypto.createHmac('sha256', secret)
    .update(`${t}.${body}`)
    .digest('hex');
  return crypto.timingSafeEqual(Buffer.from(v1, 'hex'), Buffer.from(expected, 'hex'));
}

Replay (verpasste Events nachholen)

Jedes Event hat eine monotone eventSequence pro Workspace. Wenn cb-chat Events verpasst (Outage, Restart): GET /api/workspaces/<wsId>/events?fromSeq=<letzteBekannteSeq> liefert alle Events ab Cursor.

5. master.json verifizieren

Jeder master.json ist signiert. Receiver kann verifizieren ohne den Secret zu kennen — STURM bestätigt:

curl -X POST https://playground.0711.io/api/workspaces/<wsId>/master/verify \
  -H "Content-Type: application/json" \
  -d @master.json
// → {"valid": true, "errors": []}

Sicherheits-Checkliste für cb-chat-Backend

  • WSK-Secrets nie an Frontend ausliefern (immer im Backend halten)
  • Sessions kurzlebig halten (TTL ≤ 1h)
  • postMessage-targetOrigin immer explizit setzen, nie '*'
  • Webhook-Signatur per timingSafeEqual vergleichen, nicht per ===
  • Webhook-Replay mit eventSequence-Cursor implementieren statt Events vertrauen
  • master.json-Snapshots per verlaufHash in cb-chat cachen — bei mismatch verify-Endpoint nutzen
